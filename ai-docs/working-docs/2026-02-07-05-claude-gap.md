# Spec vs Implementation Gap Analysis

**Date:** 2026-02-07
**Scope:** Full comparison of `/ai-docs/2026-02-07-initial/` specs against what was actually built in `ciam/`, `claims-api/`, and `claims-web/`.

**Method:** Every source file was read. Every spec requirement was checked. Gaps are ordered by functional value / risk.

---

## Summary

The build is remarkably faithful to the specs. All MVP pages, all API endpoints, all CIAM scripts, and the full security model are implemented. The core PoC thesis — authenticated claims CRUD with org-scoped JWT authorization — works end to end.

What's missing falls into two buckets: **deployment infrastructure** (Dockerfiles, CI/CD) and **polish items** (E2E tests, edge-case UI, minor role inconsistencies).

---

## TIER 1 — Blocks Production Deployment

### 1. No Dockerfiles

| Detail | |
|--------|-|
| **Spec** | `deployment-guide.md` §2.1 and §2.2 define multi-stage Dockerfiles for both services |
| **Built** | Neither `claims-api/Dockerfile` nor `claims-web/Dockerfile` exist |
| **Impact** | Cannot build container images. Blocks all CI/CD and Oracle VM deployment. |
| **Fix effort** | Low — the spec contains copy-pasteable Dockerfiles. `next.config.ts` already has `output: "standalone"`. |

### 2. No GitHub Actions Workflows

| Detail | |
|--------|-|
| **Spec** | `deployment-guide.md` §3.2 and §3.3 define `.github/workflows/claims-api.yml` and `claims-web.yml` |
| **Built** | No `.github/workflows/` directory exists |
| **Impact** | No automated test/build/deploy pipeline. Manual deploys only. |
| **Fix effort** | Low — the spec contains full workflow YAML. Just needs the repo secrets configured. |

## TIER 2 — Functional Gaps That Affect the PoC Demo

### 3. Viewer Role Can Create Claims (Backend)

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §3.3 role table: viewer = "See dashboard, view claim details, view timeline. **No create/edit/action.**" |
| **Built (backend)** | `POST /api/claims` allows **any org member** — no role check. A viewer can create claims via curl. |
| **Built (frontend)** | `canCreateClaim()` in `permissions.ts` correctly blocks viewer-only users from seeing the form. |
| **Impact** | UI hides it, but the API is permissive. A viewer with curl can create claims. |
| **Worth fixing?** | Yes — add role check in `ClaimService.createClaim()`. The frontend already has the logic; backend should match. |

### 4. Billing Role Permission Mismatch

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §3.3: billing = "View dashboard, view details, approve claims. **Cannot deny or create.**" |
| **Built (frontend)** | `canCreateClaim()` returns true for billing users (they're not viewer-only). Billing users see "File New Claim" in sidebar. |
| **Built (backend)** | No role check on create — any member can create. |
| **Impact** | Billing users can create claims, which the spec forbids. |
| **Worth fixing?** | Yes, if you want spec-accurate roles. Straightforward check in both `canCreateClaim()` and `ClaimService`. |

### 5. Submit Button Visible to Non-Owners

| Detail | |
|--------|-|
| **Spec** | `spring-boot-claims-spec.md` §4.2: PUT and submit = "**owner or admin**" |
| **Built (frontend)** | `ClaimActions.tsx` shows "Submit" for ALL users when status is DRAFT (`show: (s) => s === "DRAFT"`). No owner/admin check. |
| **Built (backend)** | `ClaimService.submitClaim()` correctly enforces owner-or-admin and returns 403. |
| **Impact** | A viewer sees the Submit button, clicks it, gets a 403. Bad UX, not a security hole. |
| **Worth fixing?** | Yes — pass `claim.userId` to the action visibility check and compare against session user ID. |

### 6. No Error Feedback on Failed Claim Actions

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §6: "Show meaningful error messages. Distinguish between auth errors (redirect to login) and API errors (show error toast/alert)." |
| **Built** | `ClaimActions.tsx` catches fetch errors silently — no toast, no alert. `handleAction` doesn't check `response.ok` failure path beyond just not refreshing. |
| **Impact** | User clicks "Approve", gets 403, nothing happens. No feedback. |
| **Worth fixing?** | Yes — add sonner toast on error. The toast component (`sonner`) is already installed. |

### 7. `sub` Claim Fallback to Email-Derived UUID

| Detail | |
|--------|-|
| **Spec** | All specs assume `sub` is a real Keycloak UUID: "`userId` from Keycloak `sub` claim — the claimant" |
| **Built** | `ClaimController.extractUserId()` falls back to `UUID.nameUUIDFromBytes(email.getBytes())` when `sub` is missing or not a valid UUID. |
| **Impact** | If Phase Two tokens sometimes include `sub` and sometimes don't (or the format changes), the same user could get two different userIds across sessions. Claims created with one ID wouldn't be "owned" under the other. |
| **Worth fixing?** | Investigate — log what `sub` actually contains in production tokens. If it's consistently present, remove the fallback. If it's consistently absent, the email-derived UUID is stable and fine. The danger is inconsistency. |

## TIER 3 — Quality / Testing Gaps

### 8. No Playwright E2E Tests

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §7: "E2E: Playwright — Full login flow, create claim, approve claim, org switching" |
| **Built** | No `playwright.config.ts`. No `tests/e2e/` directory. No Playwright in devDependencies. |
| **Impact** | No automated verification of the full auth flow. Manual testing only. |
| **Worth fixing?** | Yes, before handoff. Even 2-3 happy-path tests (login, create claim, approve) would catch regressions. |

### 9. Dashboard / Detail Pages Silently Fail

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §6: "Show meaningful error messages" |
| **Built** | `dashboard/page.tsx` and `claims/[id]/page.tsx` catch API errors and return fallback UI (`"Failed to load claims"` text), but no retry mechanism and no distinction between network error, 401, 403. |
| **Impact** | If the backend is down, user sees "Failed to load claims" with no way to retry or understand why. |
| **Worth fixing?** | Low priority for PoC, but adding a reload button and error type distinction would improve demo quality. |

### 10. No Client-Side Form Validation

| Detail | |
|--------|-|
| **Spec** | Not explicitly required, but §6 says "Error states: Show meaningful error messages" |
| **Built** | `ClaimForm.tsx` uses basic `useState` with no validation. User can submit empty forms. Backend returns 400 with field-level errors, but the frontend doesn't parse or display them inline. |
| **Impact** | Bad UX — user submits, gets generic error. Could be improved with zod + react-hook-form. |
| **Worth fixing?** | Nice-to-have. The backend validation catches everything; this is purely a UX improvement. |

## TIER 4 — Minor / Cosmetic / Spec Deviations (Acceptable for PoC)

### 11. `verifyEmail` Set to `false`

| Detail | |
|--------|-|
| **Spec** | `ciam-specification.md` §1.3.1: `"verifyEmail": true` |
| **Built** | `01-configure-realm.sh` sets `"verifyEmail": false` |
| **Impact** | Test users don't need to verify email. Fine for PoC. Would need to be `true` for production CIAM. |

### 12. Auth.js v5 Beta

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §9: "If v5 is still unstable, fall back to v4" |
| **Built** | Uses `next-auth@5.0.0-beta.30`. |
| **Impact** | Beta API surface could change. Currently working. The spec warned about this explicitly. |
| **Worth fixing?** | Monitor only. If upgrading to a stable v5 release, verify callback APIs haven't changed. |

### 13. Token Debugger Doesn't Decode JWT

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §3.2 feature 7: "Show the **decoded JWT** (access token and ID token)" |
| **Built** | `/dev/token` page shows the Auth.js session object as JSON. Does not base64-decode and display the raw JWT payload. |
| **Impact** | Less useful for debugging token mapper issues. You can't see the raw Keycloak claims vs what Auth.js passes through. |
| **Worth fixing?** | Nice-to-have for debugging. Add a section that decodes `session.accessToken` and displays the raw JWT claims. |

### 14. Dark Mode Toggle Not Wired

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §6: "Dark mode: Nice-to-have. Tailwind and shadcn/ui support it natively." |
| **Built** | Dark mode CSS variables defined in `globals.css`. `next-themes` is in `package.json` dependencies. But no theme toggle button exists in the UI and `next-themes` ThemeProvider is not wired into the app layout. |
| **Impact** | Dark mode exists in CSS but is inaccessible to the user. |
| **Worth fixing?** | Low priority. Wire up `next-themes` provider + a toggle button in the header if you want it for demos. |

### 15. Identity Provider Mappers Not Configured

| Detail | |
|--------|-|
| **Spec** | `ciam-specification.md` §1.3.4: Map social provider claims (e.g., Google profile picture) to user attributes |
| **Built** | Not implemented. Social login works (Google, etc.) but profile picture and other provider-specific attributes aren't mapped. |
| **Impact** | No profile pictures from social providers. Standard email/name are imported automatically by Keycloak. |
| **Worth fixing?** | No — cosmetic for PoC. |

### 16. No Organization-Specific Identity Providers

| Detail | |
|--------|-|
| **Spec** | `ciam-specification.md` §2.4.5: Link org-specific IdPs (e.g., Acme Corp's Azure AD) for B2B federation |
| **Built** | Not configured. Only social providers (Google, Microsoft, Facebook) are set up. |
| **Impact** | B2B federation isn't demonstrated. This is an advanced CIAM pattern. |
| **Worth fixing?** | Only if you want to demo B2B IdP federation. Requires a second IdP to federate with. |

### 17. No Logout / Single Logout Configuration

| Detail | |
|--------|-|
| **Spec** | `ciam-specification.md` §3.8: Front-channel and back-channel logout patterns |
| **Built** | Auth.js `signOut()` clears the local session. No Keycloak SLO redirect. No backchannel logout URL registered on clients. |
| **Impact** | Logging out of Next.js doesn't log out of Keycloak. User can re-authenticate without entering credentials until the Keycloak session expires. |
| **Worth fixing?** | Depends on demo goals. For a clean logout demo, wire Auth.js signOut to redirect to the Keycloak logout endpoint with `id_token_hint`. |

### 18. Service Client (Client Credentials) Not Used

| Detail | |
|--------|-|
| **Spec** | `spring-boot-claims-spec.md` §3.2: "For service-to-service calls (e.g., calling the Keycloak Admin API), the backend uses the `poc-backend` client" |
| **Built** | `poc-backend` client is registered in Keycloak but the Spring Boot app never uses it for outbound calls. No `OAuth2AuthorizedClientManager` or client credentials flow implemented. |
| **Impact** | None for current features — the backend only validates incoming JWTs. Would matter if you add features that call Keycloak's Admin API. |
| **Worth fixing?** | No — not needed for current scope. |

### 19. `ALLOWED_ORIGINS` Supports Only Single Origin

| Detail | |
|--------|-|
| **Spec** | `spring-boot-claims-spec.md` §3.4: env var `ALLOWED_ORIGINS` |
| **Built** | `SecurityConfig.corsConfigurationSource()` splits on comma, so it does support multiple origins. |
| **Impact** | None — this works correctly. |

### 20. Admin Review Page Not Route-Protected by Role

| Detail | |
|--------|-|
| **Spec** | `nextjs-claims-app-spec.md` §3.1: Admin Review Queue — "Yes (admin role)" |
| **Built** | `middleware.ts` only checks authentication, not roles. Any authenticated user can navigate to `/admin/review`. The page fetches SUBMITTED/UNDER_REVIEW claims and shows them. The sidebar hides the link for non-admins, but the route itself is accessible. |
| **Impact** | Non-admin users can see the admin review queue by typing the URL directly. They can't take actions (backend enforces roles), but they can see the list. |
| **Worth fixing?** | Yes, for a clean demo. Add a role check at the top of the page component and redirect non-admins. |

## Things That Exceeded the Spec (Positives)

| Item | Detail |
|------|--------|
| **Close endpoint** | `POST /api/claims/{id}/close` — not in spec table but logically required for APPROVED/DENIED → CLOSED transition. Correctly implemented. |
| **Idempotent CIAM scripts** | All setup scripts use helper functions to check-before-create. Safe to re-run. Spec didn't require this. |
| **Comprehensive security tests** | `SecurityTest.java` tests multi-org isolation, billing-specific permissions, missing headers. Goes beyond spec requirements. |
| **OrgContext filter** | Clean separation of org validation from controller logic via servlet filter + value object pattern. |
| **Token refresh** | Auth.js jwt callback correctly implements refresh token flow with error flagging. Middleware catches `RefreshAccessTokenError` and redirects to login. |
| **Standalone Next.js output** | `next.config.ts` already has `output: "standalone"` — ready for the Dockerfile that doesn't exist yet. |

## Recommended Fix Order (If Continuing)

1. **Add Dockerfiles** — copy from deployment-guide spec, test `docker build`
2. **Add GitHub Actions workflows** — copy from deployment-guide spec
3. **Add error toasts to ClaimActions** — 10 minutes, big UX improvement
4. **Restrict viewer/billing from creating claims** (backend + frontend) — 15 minutes
5. **Add role check to admin review page** — 5 minutes
6. **Fix Submit button visibility** (owner or admin check) — 10 minutes
7. **Investigate `sub` claim behavior** — log it, decide if fallback is needed
8. **Add 2-3 Playwright E2E tests** — login + create + approve happy path
9. **Wire up Keycloak logout redirect** — 15 minutes
10. **Set `verifyEmail: true`** in realm config — 1 line change
